# Owner process consistency review

## Scope and ownership

This review follows intake, capability discovery, evidence selection, task
compilation, capacity allocation, atomic admission, dispatch, persistent context,
correction, final review and revision. It changes shared compiler and worker
boundaries, not the scheduler. Native execution remains registry-owned; semantic
content and independent judgments remain model work.

The first compiled-owner release selected delegation policy 3. Explicit policies 1 and 2 keep their
captured task interface and do not gain compiler-generated tasks. Policy 3
requires indexed working context and the registered producer/handoff compiler.
Historical requests, grants, failed attempts, artifacts and review obligations are
not migrated or accepted by this implementation.

## Findings and implemented changes

| Boundary | Inconsistency | Shared correction |
| --- | --- | --- |
| Discovery | Compact briefing omitted task limits and presented an upper work bound as actual work | Show authorized and remaining capacity separately, effective request ceilings, registered unit costs and available partition/merge support |
| Evidence | JSON media type hid whether a prior catalog satisfied a registered contract | Validate available artifact contract/role/seal and native source receipts for discovery; untyped evidence stays untyped and requires a registered content producer |
| Input selection | Several JSON evidence files competed for one native data port | Policy 3 has a separate data reference for single-JSON adapters; keep worker evidence and native payload roles distinct, with original ancestry retained for review |
| Proposal shape | Native operations and workers shared ambiguous optional fields | Native task intents have a separate schema variant; code owns native outputs, worker selection and file bindings |
| Review planning | Owner had to supply required record reviewers | Expand missing reviewers from registered content requirements and count them against the original task grant |
| Workload | Owner path bypassed normal planning's partition compiler | Derive known subject counts from exact inputs and reuse the registered capacity, partition and reviewed-merge compiler; retain upper bounds for unavailable future evidence |
| Final inspection | An upstream review could block the renderer needed by that review | Render the candidate before reviewing the terminal visual representation, with exact ancestor files and registered page evidence |
| Whole-file acceptance | Eliding a structural merge review could leave a requested final JSON without final review | Preserve a whole-final-candidate review even when intermediate merges can use deterministic structural verification |
| Preflight | Admission could accept saved source data that claim rejected | Reuse Runtime.checked_inputs for fully available inputs before admitting any tasks; keep identical late-bound checks for future outputs |
| Transactions | Retrying an expanded intent could rebuild a different graph as state changed | Return the exact committed receipt for the same original intent; reject changed intent IDs; commit the full expansion atomically |
| Context | Archived history exposed opaque provider signatures as readable text | Keep raw journals intact and expose separate semantic call/result/decision views, including when a raw archive ID is requested |
| No progress | Repeated reads and text-only responses could spend the whole invocation | Stop after three identical no-effect outcomes, without scheduling another invocation or accepting completion |
| Owner capacity | Last invocation could launch children with no invocation left to finalize | Require a remaining owner invocation before a new delegation; never increase the grant implicitly |

Required reviewers, partitions, merges and previews all consume existing slots.
Operations are selected only from the frozen grant. Source facts are not promoted
by schema validation, and old JSON is not given a fabricated completion seal.
The admission transaction saves compiler decisions alongside the original intent:
exact workload source/hash, proposed and measured bounds, generated reviewer,
partition decisions and derived budgets. A retry returns the original receipt.
The final quality gate still requires exact current candidate versions, resolved
findings, independent judgments and actual rendered-pixel observations.

## Qualification and limits

Small fixtures exercise incomplete task proposals through real compilation,
record workers, independent review, restart, native merge, correction and final
delivery. They include insufficient slots, missing merge authority, unproven
sources, atomic rollback, idempotent retry, repeated invalid responses, provider
history variants, final review retention and exhausted owner capacity. Existing
native PPTX/photo correction, pagination, provider recovery and connector tests
remain part of the affected integration scope.

A runtime candidate is assembled from the installed runtime plus the affected
modules, with every imported product module and cumulative overlay hash checked.
This is runtime qualification, not a signed application installation or live
provider qualification. Exact commands, initial failures, test counts and replay
limitations are kept in local qualification records.

The final runtime candidate passed 171 affected controlled tests. All imported
product modules and 139 cumulative overlay hashes matched the candidate. Static
conformance covered 47 registered interfaces: 1,889 directed port pairs require
runtime validation and 3,093 are incompatible; this is not an execution count.
Every interface exposed parameter schemas and producer binding metadata.

Saved failed proposals can be rehearsed on an isolated database using their
original artifacts. A successful compiler replay does not authorize live
admission, establish semantic research quality, or add remaining owner turns.
The preserved live job remains blocked with its original allowance.
Both saved failed collection proposals compiled from their exact original inputs
in the isolated positive rehearsal. The actual remaining owner allowance instead
held before admission. The positive rehearsal assumed one additional invocation
in memory only; it did not authorize or change live capacity. An earlier rehearsal
missed this finalization requirement and is retained as superseded evidence.

## Installed qualification and explicit continuation capacity

The maintained application package subsequently passed 173 affected controlled
checks, including exact capacity-authorization receipt validation, atomic rollback
and finding preservation. Native and Python versions are 0.13.219. Stable signing,
whole installed-bundle equality, all 139 runtime overlays, the running app and five
fresh core services were verified. Existing job plans, attempts, artifact hashes,
request journals and dispatch controls remained unchanged through installation.
The pre-existing Messages permission warning is separate from core health. No
paid continuation or final delivery is claimed by these installation checks.

Trusted continuation admission still defaults to remaining capacity only. When a
user explicitly approves an increase, the same inheritance transaction can accept
a receipt containing the exact approval question/reply, predecessor and successor
identities and plan hashes, and exact additional owner/task capacity. This is not
an owner tool: the trusted caller must obtain actual user authorization. Missing,
stale or mismatched receipts reject admission. Old grants remain unchanged;
provider, per-task limits, operation scope and evidence checks remain mandatory.
Original review findings survive the transfer and still require exact independent
resolution. Synthetic approval fixtures never authorize real work.

Arbitrary tool sequences remain invalid when their ports, evidence or permissions
are incompatible. Missing semantic information still needs research or a model
judgment. Future adapters must declare those contracts and pass compatible-flow
qualification; this review is not a guarantee that every future tool or provider
will succeed.


## Canonical owner proposals and bounded correction (policy 4)

The later saved failure exposed a wire/local mismatch. Gemini's legacy projection
merged the native and worker object alternatives, including their optional fields
and intersecting their required fields. The failed proposal therefore satisfied
the advertised wire while violating the local native/content output rules. The
owner then received only a generic alternative-mismatch error. This was an
interface defect, not evidence that the model had ignored the advertised schema.

Prospective policy 4 sends the same canonical delegation JSON Schema used for
local validation through Gemini's `parametersJsonSchema` field. This field is
[documented by Google](https://ai.google.dev/api/generate-content#FunctionDeclaration).
Native, registered-content, review and ordinary worker variants are distinct.
Operation/content/review output ports belong to code; only ordinary workers name
outputs. The brief states that distinction directly. Registry-specific semantic
parameters still come from the selected catalog, and all authorization, reference,
capacity and content checks remain local. Previously admitted policies retain
their wire shapes; finish/report transport remains unchanged. AUTO mode is retained.
No live acceptance of this prospective declaration is claimed.

Confirmed uncommitted delegation rejection now enters a correction phase within
the existing owner Session. Existing production events preserve the exact rejected
proposal, diagnostic and correction counters. The pending proposal is pinned in
current state on each request and restored after restart. Compacted context does
not advertise archive retrieval during this phase. Diagnostics identify every
code-owned output field in the proposal; other alternative errors retain their
specific branch failures.

Only delegation and contract lookup remain available. The actual tool dispatcher
also enforces the restriction, including calls returned in the same response or
calls to tools absent from the current declaration. Two corrective submissions
after the first rejection and two contract lookups fit inside the existing request
and tool ceilings. Two ignored correction instructions, a third lookup, or a third
rejected proposal hold without automatic wake. Changing request IDs or restarting
does not reset those counters. Successful admission saves the correction's
resolution together with its graph and receipt. Atomic rollback permits correction;
a committed receipt or uncertain work instead requires reconciliation. This adds
no scheduler, external retry, new live capacity or inferred acceptance.

Controlled checks use actual runtime, worker loop, bindings, fragment stores,
review gates, native text execution, context projection and SQLite transactions,
with scripted model replies. They test corrected content through execution, review
and completion; corrected native work; rollback and duplicate admission; restart;
invalid containers/references; unchanged historical wire behavior; and blocked
history/lookup loops. A read-only-source database clone also replayed the exact
failed five-task proposal against all 21 original references and five carried
findings. Its original wire accepted the invalid shape. Removing only the five
`outputs` fields admitted the original tasks plus two required reviewers within
the remaining five owner turns and sixteen task slots. The copied graph was not
executed against retailers, Gemini, or a renderer. Both original and corrected
intents and receipts remain in private storage.

116 affected controlled checks passed, then 24 focused context/wire checks and 13
recovery checks passed after final changes. Initial fixture failures and commands
are retained in `outputs/owner-submission-recovery/CHECKS.md`. This is source
qualification, not installed-package qualification or a successful live job. The
installed app, paused continuation, historical artifacts and grants are unchanged.
A live model may still reject or fail to correct; code now prevents that failure
from turning into the observed history-reading loop. Package qualification and
separately authorized live evaluation remain the next steps.
