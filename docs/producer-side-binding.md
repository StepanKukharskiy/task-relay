# Producer-side schema binding

For newly admitted graphs, the compiler follows each registered consumer input
back to its producer before dispatch. The consumer's interface selects the
producer contract. The model selects content within that contract; it does not
design the interchange document. Normal planning and persistent-owner delegation
use the same compiler and transactional record engine.

## Registered boundaries

All 47 current operation adapters declare a handoff policy. Ports distinguish
bounded preparation data, typed content records, exact tool-generated evidence,
and ordinary declared context or native files. A new adapter supplies this
metadata through the existing adapter interface; unknown interfaces gain no
implicit compatibility.

Fifteen preparation targets share the `operation.preparation` record family:
prepared source queries, Blender scene and mesh specifications, PPTX edits,
media composition, HyperFrames preview, Rhino library geometry, Blender/Rhino/
Rhino-library/Grasshopper/SketchUp script checks, Rhino render settings, Blender
animation and asset imports. Existing document layout, collection, subject and
review families retain their own registered content contracts and lifecycle.

The shared writer exposes bounded field, item or map-entry fragments. Code owns
the document envelope, versions, ordering, declared asset aliases, exact input
hashes and output serialization. Registered validators check relationships
between fields when sealing. Invalid fragments cannot replace committed state;
incomplete data cannot release a native consumer. Structural validation is not
independent semantic acceptance.

Source packs, observed image manifests and verification receipts must originate
from their registered evidence producers. A model cannot satisfy those ports by
writing plausible JSON. Shared artifact references bind producer and consumer
to the same bytes. Saved untyped artifacts require a new preparation assignment;
executed assignments are never retroactively rewritten.

## Execution and recovery

Compatible declared-file workers receive the existing record tools. Codex CLI
workers use a workspace-local transport for those same tools. CLI fragments are
untrusted staged data until the existing controller observes confirmed successful
completion and imports them through the authoritative record engine. Failed,
pending or uncertain execution does not authorize import. An invalid batch rolls
back atomically. CLI workers do not gain access to the production database.

Binding preserves frozen ceilings and can reduce allowances to the selected
worker's capacity; it cannot raise them. Conflicting consumers, ambiguous source
bindings or insufficient capacity fail admission before dispatch. Shared binary
assets use the consumer's exact local aliases before the producer sees its
assignment. New policy is captured in the graph or owner grant; historical grants
retain their policy. Connector identities include preparation schema definitions.
Changed connector definitions require revalidation under a new admission.

## Qualification and limits

Controlled integration checks execute the real compiler, worker tool loop,
transactional store, scheduler, native source collector and PPTX renderer with
scripted model replies and HTTP research fixtures. Positive flows cover:

- Query preparation, collection, typed catalog, independent review, slide
  projection and a real PPTX for plant, component and furniture field definitions.
- Layout fragments through a real PPTX, followed by a data-only edit after
  reopening the controller, preserving the original artifact and assignment.
- All 15 preparation targets through compilation, fragment submission, store
  reopening, projection export and their registered validators.
- CLI staging through confirmed import and native rendering, failed-import
  rollback, repeated submission, incompatible consumers and exact asset aliases.

The main affected integration suite passed 136 tests. Subsequent focused checks
passed 37 tests after connector identity and CLI boundary changes. Counts overlap.
Detailed commands, final instruction checks and retained failed development logs
are recorded in ignored local qualification output.

This is source qualification, not an installed or live result. Host applications,
video rendering, browsers and live providers were not exercised by these checks.
The adapter matrix classifies compatible boundaries; it does not prove every
possible graph, model decision, factual claim or final visual result. Exact
package qualification and installation remain necessary before another paid run.

## Owner-facing context

The subsequent live trial never reached delegation: the owner repeatedly read
catalog definitions and archived excerpts. Passing handoff tests did not establish
that it could efficiently choose and execute work.

Prospective working-context policy 2 projects one exact request, declared evidence
references, delivery requirements and capacity into the owner role. Specialists
retain the exact source text, pixels and code-bound schemas. Owner discovery uses
registered interfaces without duplicating full worker-authoring payloads. The
shared view retains selected capability exchanges while reading evidence,
collapses only identical read observations and preserves complete journals and
reasoning/tool groups. Stable historical exchange references replace growing
archive-of-archive prompts. Nothing discarded from the model's working view is
silently discarded from the saved record or treated as accepted evidence.

The existing controller cannot automatically renew an exhausted observation-only
invocation without pending delegated work. Historical grants retain their captured
context policy. Source qualification includes positive compaction through actual
PPTX construction/revision and restart without a repeated no-progress invocation;
package qualification and installation are recorded separately. Live completion
remains unproven.

## Owner task intents

Prospective delegation policy 2 replaces the JSON-string assignment envelope
with a structured `tasks` argument. The owner supplies an objective, exact input
references, logical output names and desired formats, or a registered operation.
It can request an independent reviewer by naming `review_of`. Code adds the
candidate files, inherited evidence, dependencies and review obligations.

For example, a content worker can declare an output named `layout`, and the
render task can select `{"task":"content","output":"layout"}`. Neither task
chooses a workspace path. Declaring both tasks together lets the existing
producer-binding compiler select the registered layout fragment schema before
the worker starts. For an explicitly selected content family, code also declares
its JSON and summary outputs. The model supplies only semantic field choices.

Operation adapters declare which parameters reference files or exact hashes.
The owner supplies artifact or task/output references in those fields; code
resolves paths and verifies artifact bytes. Hash-valued operation parameters
require an existing artifact: a consumer that needs a future artifact's hash
must be delegated after that artifact completes. The owner never supplies the
hash literal. Preparation manifests continue to use the existing code-owned
baseline hash bindings.

Safe input names already bound by intake remain usable. New output inputs receive
isolated aliases. Saved producer provenance can restore earlier asset names only
for evidence explicitly authorized in the new grant. Missing authority and
ambiguous aliases do not import another job's evidence or rewrite the baseline.

The owner prompt carries the exact request, artifact labels and provenance,
requested deliverables, available operations and remaining capacity. It omits
file hashes, workspace paths, worker envelopes and duplicate technical rules.
Selected catalog entries expose operation choices and logical output ports;
worker schema details stay with the worker. A catalog request advertises its
three-operation limit, and an artifact read needs only its reference unless a
particular offset or size is needed.

The compiler commits original intents and resulting assignments through the same
transaction and scheduler as earlier delegation. Failed batches roll back, retry
identities cannot create duplicate work, changed bytes remain rejected, and
independent final review remains mandatory. Historical jobs and revisions retain
their captured delegation policy. This is an admission interface, not another
execution controller.

Source qualification passed 93 affected controlled checks, including actual
worker delivery/review, restart, compaction followed by delegation, real PPTX
creation and revision, and reuse of exact prior image bindings. Registered field
configurations and a new synthetic adapter use the same compiler. Model replies
and research are scripted; these checks do not establish live efficiency or
professional quality. This delegation policy is not installed or live-qualified.

## Review findings across corrections

New owner jobs and newly compiled plans capture review_followup_version 1.
Historical plans without that policy retain their report contracts. The existing
checks_recorded journal supplies immutable finding identities and original
review/candidate references. No additional reviewer, scheduler or recovery budget
is introduced.

Correction workers receive the concrete issues. At dispatch, code binds one
additional structured check in an independent reviewer’s existing report form.
Each issue needs a resolved/unresolved judgment and precise inspected locations
on the current candidate. Code checks complete coverage, exact input bytes and
new candidate/evidence identity. Missing judgments, unchanged bytes presented as
a repair, unresolved judgments disguised as advisories, and changed frozen
inputs cannot establish closure. Report fragments and normal finalization use
the same validator. A renamed replacement task cannot discard job findings.

Owner final-file reviews carry job-level findings, including failed intermediate
reviews; final delivery requires a review covering every recorded issue. Such a
review must receive the evidence for the complete outcome. This is deliberately
a whole-outcome gate, not permission for a small unrelated helper to approve the
job. In ordinary fixed graphs, findings follow the reviewed task; a correction
producer also receives the exact downstream review that scheduled its repair.
Native execution does not receive extra model checks. Existing attempt/task
limits, uncertain-action reconciliation and user decision boundaries still apply.

Resolution of meaning, image suitability and factual support remains an
independent semantic judgment. Explicit coverage prevents forgotten findings;
it cannot prove that a model judgment is truthful. Actual final visual inspection
remains required by the existing final-quality contract. Controlled tests use
scripted judgments and do not establish unattended live success.

## Table layout and typography

The built-in table template now owns a readable 14–16pt font range, conservative
wrap estimates, explicit row heights and repeated-header pagination. Rows that
are too dense for the original column arrangement become field/value detail
tables in record order. Every original value remains represented. A cell that
cannot fit even in that arrangement fails explicitly instead of being silently
clipped or shrunk below the font floor. The existing deck-size ceiling remains.

Producer schemas advertise the actual title/caption limits. The same pure-Python
pagination implementation is included in isolated validators and frozen layout
support identities. Native save/reopen verification checks row geometry, text
and typography. Font substitution on another host may still affect wrapping;
these conservative estimates do not replace the rendered-page quality review.
Custom explicit geometry is not silently rewritten.

Trusted owner continuation admission can carry prior findings through a captured
`review_findings_inherited` event. This is not an owner tool or an authorization
grant. Admission must be explicitly authorized and atomic with successor creation.
The shared boundary checks exact request/provider, original evidence scope,
quiescent predecessor, unchanged worker limits and remaining invocation/task
capacity. It preserves finding identities and original review input provenance;
acceptance is never inherited. Exact retries are idempotent, another successor
from the same predecessor is refused, and final review must close inherited as
well as newly observed defects. Historical grants and artifacts stay unchanged.

Gemini wire projection is separate from the local schema contract. Concrete tool
fields stay structured; open maps and heterogeneous unions use encoded JSON
values, decoded by code before the same compiler/validator. The model does not
own assignment envelopes, paths or evidence hashes. Persisted declarations
project canonically. Controlled tests inspect actual emitted function declarations
and decoded handoffs; they do not prove external server acceptance. A confirmed
first-request rejection can use an original remaining attempt through the shared
continuation registry only with no tool effect or pending response and an exact
changed projection proof. No grant or attempt counter is reset.
