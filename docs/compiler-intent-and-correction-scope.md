## Operation intent

New delegation-v4 jobs default to worker-tools-v3. The owner chooses one explicit
mode. Catalog discovery and the compact decision brief expose the same compiler
choices; neither guesses the mode from a filename or MIME type.

- `execute`: consume exact existing inputs. For a registered single JSON port,
  supply `data: {artifact: ...}` or `data: {task: ..., output: ...}`, or the
  operation's registered parameter reference. No content-authoring tools or
  generated content output are added. Other JSON evidence remains inspectable
  and is excluded from that operation's selected data port.
- `create`: authorize new bounded fragments through the operation's registered
  preparation interface. Code owns document envelopes, assembly and outputs.
- `revise`: authorize bounded content preparation with an exact `baseline`
  reference. The baseline remains immutable and is validated using the native
  operation contract. This is not automatic semantic diffing or a promise to
  preserve every unedited fragment; the worker prepares a new candidate and
  independent review must assess the requested changes.

A mode unavailable through registered compatible interfaces is refused. Existing
native `operation` intents still execute their registered inputs directly. No
provider or domain changes the routing rule.

Input binding and native preflight happen before worker dispatch. Already saved
invalid inputs reject the owner batch atomically. A future producer's incompatible
result blocks its consumer before a worker attempt is spent. These checks reuse
Runtime's native preflight and registered validators; they do not execute a host
operation or expand its authority. Exact-script approval remains a separate gate.

## Correction responsibility

New delegation-v4 jobs capture `correction_scope_version: 1`. A task can declare
`repairs: [finding_id, ...]`, selecting known findings in this job. Code preserves
that selection in the executed assignment and derives the helper's review from
that exact candidate. A reviewer cannot independently choose a smaller subset.

A scoped helper is responsible only for its named findings, including when its
output has the same media type as a final deliverable. Full evidence remains
available; this policy narrows obligations, not access or historical journals.
Unrelated downstream findings do not become extra helper acceptance criteria.

An unscoped final candidate's review still receives all applicable findings.
The existing delivery gate verifies exact candidate judgments and complete job
finding coverage. Accepted partial repairs cannot complete the job. Corrections,
independent judgments and restart preserve the original findings and versions;
there is no globally mutable resolved flag.
