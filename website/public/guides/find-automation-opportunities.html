Task Relay guides

Find automation opportunities in recurring forum complaints

Turn repeated “how do I stop doing this?” questions into a list of specific workflows worth testing.

Searching, collecting links, recognizing repeated problems and checking whether a tool can help is itself recurring work. A research worker can prepare the evidence and proposed recipes for your review.

Define the audience and the product boundary

Choose a few communities and a capability summary. For example, architecture forums plus document and data workflows that a local agent can execute. Give the worker your previous findings so it can preserve existing IDs and avoid rediscovering the same threads.

Download the reusable research request

Find 20 repetitive-work problems discussed in these public communities:
[communities]. Compare them with the attached capability summary.
For each, retain the source URL and date, a frustration paraphrase,
current workaround, inputs, desired output and a proposed how-to article.
Separate independent recurring requests, single examples, promotional
posts and hypotheses. Do not invent search volume or time saved.
Return a deduplicated backlog and five candidates for a practical pilot.
Stop at the research artifacts; do not post replies or contact anyone.

Search for the work, not just the word “automation”

Useful queries combine a task with phrases such as manually, every week, takes hours or is there a way. Search specialist forums as well as broad communities.

For example, a bookkeeping request identifies the desired invoice filename fields. A CSV consolidation request identifies source tools, repeat frequency and a failed workaround. Those details help define a testable recipe.

Separate evidence from recommendations

  • Observed: what the original poster actually says.
  • Repeated: another independent request for substantially the same outcome.
  • Proposed: the narrower workflow your product could deliver.
  • Unproven: willingness to pay, market size or time saved until measured.

Count a cross-post once. Multiple replies in one thread can strengthen a lead, but they are not independent threads. Keep promotional “I built a tool” posts separate from firsthand help requests. A single useful example can still justify a small pilot if it is labeled honestly.

Ask for a useful result

Each backlog row should include the audience, source, repeat trigger, input files, intended output, required tools, implementation gap and an article title. Rank candidates by evidence and by how clearly you can demonstrate a correct result.

The next step is one bounded pilot with representative inputs. Save the procedure and results, then write the article from what actually happened. New searches should create a new backlog version and retain earlier decisions.

The initial research behind these guides produced 20 candidates with source and capability notes. It ran in the development task; this reusable brief has not yet been executed by the installed Relay service. No forum outreach, automated posting or recurring monitor is included.

Try it with your own task

Set up Task Relay, connect a suitable worker and begin with a small representative input. Review the first result before repeating the workflow.
